# ADR-0030: 録画中は同じ番組の終了時刻延長だけを反映する

- Status: Accepted
- Date: 2026-08-09
- Deciders: Project owner, Codex（v1.0までの委任範囲）
- Supersedes: None
- Superseded by: None

## 背景

v0.0.5は録画開始前の予約を完成済み番組表へ追従させる。録画処理を作った後は、保存中のstreamと終了期限が既に動いているため更新しない。このままでは延長番組が元の終了時刻で切れる。

Mirakurunの番組一覧にはTSIDや番組世代番号がない。一方、v0.0.5では同じbackend、service、event ID、観測間隔、開始時刻、放送時間の固定上限から、予約追従に限った後継関係を判定できる。録画中もこの判定を狭い用途だけに使える。

## 決定

追従を要求した予約について、同じ番組の検証済み後継が次の条件をすべて満たす場合だけ、録画中の終了時刻を延ばす。

- 予約と後継番組の開始時刻が同じ。
- 後継番組の終了時刻が現在の予定終了時刻より後。
- 番組の放送時間は60秒以上12時間以内で、既存の後継判定上限も満たす。
- 録画処理は一件だけで、状態が`CLAIMED`、`STARTING`、`RECORDING`のいずれか。

一つのSQLite transactionで、予約のrevisionと放送時間、録画処理の予定終了時刻を比較更新する。録画処理が完了処理へ入った後、利用者が予約を変えた後、または比較対象が変わった後は更新しない。短縮、開始時刻変更、別サービスへの切替えは行わない。

録画処理は既存の5秒ごとの進捗保存時にDBの予定終了時刻を読み直す。進捗保存の戻り値へ終了時刻を加え、別の監視goroutineやqueueは作らない。stream contextの絶対上限は、録画処理を確保した時点の終了時刻と番組開始から12時間後の遅い方とする。DBから読んだ終了時刻が現在値より前、または絶対上限より後なら録画を延ばさない。

番組表の既定更新間隔は5分とする。明示設定できる5分から24時間の範囲は変えない。通常起動時の暗黙接続先や自動再試行は追加しない。

## 理由

録画中の利用者価値が高いのは、延長による末尾欠けを防ぐことである。短縮や開始時刻変更まで反映すると、保存済みデータを捨てる判断や別番組との境界判断が必要になる。終了時刻を後ろへ動かすだけなら、既存ファイルを失わずに実装できる。

進捗保存と同時に終了時刻を読む方法なら、DBを正本にしたまま、現在の一件録画構造を保てる。新しい常駐処理やschemaも不要である。

## 影響

- 実行中の録画は、DB更新を最大約5秒で読み取る。
- streamの読み込み停止中は、既存の10秒無進行上限まで終了判定が遅れる場合がある。
- 5分ごとの番組表取得によりMirakurunへの読み取り回数は増えるが、既存の件数、本文、時間、直列実行の上限を維持する。
- Mirakurunのservice identityは引き続き`PROVISIONAL`であり、一般的な同一性保証には使わない。

## 採用しなかった案

### 一分ごとに録画処理だけを確認する

番組一覧取得と録画監視の二つの定期処理が必要になるため不採用。既存の番組表更新と5秒進捗保存を使う。

### 現在のcontext deadlineを後から延長する

Goの`context.WithDeadline`は期限を後から延ばせない。最大期限を先に固定し、通常終了はDBの値で判定する。

### 終了時刻の短縮も反映する

誤判定時に録画データを取り戻せないため不採用。
