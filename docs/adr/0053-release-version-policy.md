## 背景

Sazanami DVRはv0.0.1からv0.0.29まで、機能追加と修正の多くを末尾の数字で進めてきた。短い間隔で
公開する初期段階には使いやすかったが、利用者は版番号だけでは新機能を含む更新か、修正だけかを
判断できない。並行する機能PRが同じ版番号と変更履歴を編集する問題もある。

Project ownerは、三つの数字をメジャー版、機能追加・改修、修正に分ける方針を採用した。さらに、
現在の機能群をv0.1.0へまとめ、v0.9.0を72時間試験前の機能完成版、v1.0.0を長時間試験後の安定版に
することを明示した。

## 判断

製品版は`vX.Y.Z`とし、各数字を次のように使う。

| 数字 | 用途 | 例 |
|---|---|---|
| `X` | メジャー版。v1.0以後の公開契約を意図的に壊す変更 | v1.0.0からv2.0.0 |
| `Y` | 利用者向け機能、挙動変更、まとまった改修 | v0.1.0からv0.2.0、v1.0.0からv1.1.0 |
| `Z` | 新機能を含まない不具合、小さい内部変更、文書、配布の修正 | v0.1.0からv0.1.1、v1.0.0からv1.0.1 |

`Y`を進めるときは`Z`を0へ戻す。`X`を進めるときは`Y`と`Z`を0へ戻す。v1.0より前は開発版として
`X=0`を維持する。v0で互換性へ影響する変更が必要な場合も、変更内容と移行方法を明記して`Y`を進める。

公開済みのv0.0.1～v0.0.29は履歴として維持する。次の機能版はv0.0.30ではなくv0.1.0とする。
Handoffs 0039～0042の機能PRでは版番号と変更履歴を更新しない。四つが製品`main`へ統合され、
各結果を読み戻した後に、専用のHandoff 0043とrelease-prep PRで一度だけ更新する。
公開配布物がなければ実行できない確認だけが残るhandoffは、`In Progress`のまま確認項目を
release handoffへ引き継ぐ。公開後に結果を元のhandoffとrelease handoffの両方へ戻してから完了する。

機能PRを統合している間、製品`main`の版表示は最後の公開版を維持する。この状態からtagや配布物を
作らない。専用PRで製品版、版表示test、READMEの現在版、変更履歴、対応範囲を同じコミットへ揃え、
完全なコミットSHAのCI成功後にだけtagを作る。

v0.9.0は、Plan 0040が定めるv1.0条件のうち、実験用Ubuntuで行う連続72時間試験だけを残した
リリース候補とする。対象版KonomiTV／Komorebiの操作、導入、更新、切り戻し、復旧、短い実環境確認、
自動テスト、配布物、公開文書はv0.9.0までに完了させる。

v1.0.0は、最終候補と同じ製品コード、設定、配布処理のコミットで72時間試験に合格し、試験中に
見つかった問題を修正した後に公開する。実行時の挙動を変える修正を加えた場合は、新しい候補で
72時間試験をやり直す。v1.0.0以後は、修正をv1.0.1、機能追加をv1.1.0として進める。

版番号は互換性の証拠ではない。KonomiTV／Komorebiの対応状態は、固定版の呼び出し調査、契約test、
実環境結果、製品コミットを根拠に互換実装表で管理する。SQLite schema versionも製品版とは別に管理する。

公開済みtagは移動、削除、再利用しない。公開後に問題が分かった場合は、次の修正版で訂正する。

## 影響

- 利用者は二つ目の数字で機能追加、三つ目の数字で修正だけの更新を見分けやすくなる。
- 並行する機能PRから版番号と変更履歴の競合を外せる。
- リリース準備は機能統合後の独立PRになるため、統合途中の`main`は公開版と同じ版を一時的に表示する。
- v0.9.0とv1.0.0の間には、最終候補を固定した72時間試験が必要になる。
- 版番号だけでクライアント全体への対応を表明できない点は変わらない。

## 採用しなかった案

### v0.0.30以後も末尾だけを進める

機能追加と修正を区別できないため採用しない。

### 各機能PRで版番号を進める

未統合の変更が次版を名乗り、同じ行の競合も増える。統合後の専用PRへまとめる。

### v0.9.0を安定版として扱う

72時間試験前の候補であることが伝わりにくい。0系はpre-release、v1.0.0を最初の安定版とする。

### 版番号とDB schema versionを一致させる

製品修正とDB変更の頻度が異なり、復旧判断を誤りやすい。二つの番号は独立させる。

## 見直す条件

- 複数の保守系列を同時に提供する必要が出た。
- 公開Go APIを追加し、標準Semantic Versioningとの厳密な整合が必要になった。
- 配布方式が複数になり、同じ製品版のartifact識別を追加で定める必要が出た。
- 72時間より長い安定性試験を正式な公開条件へ加える証拠が得られた。
