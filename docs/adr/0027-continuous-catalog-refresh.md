# ADR-0027: 録画プロセス内で番組表を安全に更新する

## 背景

v0.0.1の`recording serve`は、SQLite、予約、録画、CtrlCmdを一つのプロセスで所有する。一方、番組表の取得は別の`catalog sync`コマンドであり、録画プロセスがSQLiteを開いている間は実行できない。このままでは、録画を止めずに番組表を更新できず、番組時間の変更追従や自動予約も追加できない。

単に最新の完了世代を各問い合わせで読む方式にも問題がある。CtrlCmdの一つの要求を処理している途中で新しい世代が完了すると、チャンネル一覧と番組一覧が別の世代になる可能性がある。また、チャンネル設定と合わない世代を完了扱いにしてから検証すると、次回起動時に以前の利用可能な番組表へ戻れない。

## 判断

`recording serve`をSQLiteの唯一の所有者としたまま、同じプロセス内でMirakurunの番組表を定期更新する。別の常駐プロセス、内部メッセージバス、新しいデータベース形式は追加しない。

更新は次の順で行う。

1. Mirakurunからサービスと番組を既存の上限内で取得し、`RUNNING`世代へ保存する。
2. その世代のサービスだけを読み、チャンネル設定と照合して新しいスナップショットを準備する。
3. 照合に成功した場合だけ世代を`COMPLETED`へ変更する。
4. 完了後、プロセス内の参照先を新しいスナップショットへ一度に切り替える。

照合、完了、切り替えのどこかで失敗した場合は、直前まで利用していたスナップショットを維持する。`RUNNING`世代は失敗として閉じ、次の定期更新まで即時再試行しない。

### 世代を固定して読む

各スナップショットは、バックエンドIDに加えて番組表世代IDを保持する。サービス、番組検索、予約対象の照合は「その時点の最新」ではなく、スナップショットが持つ世代IDを明示して読む。

CtrlCmd routerは要求フレームを受け取った時点でスナップショットを一度だけ取得し、その要求が終わるまで同じ値を使う。予約追加も操作開始時に一度だけ取得する。これにより、更新と同時に番組表を読んでも、一つの操作の中で世代が混ざらない。

古いスナップショットを参照中の要求はそのまま完了させる。新しい要求だけが切り替え後のスナップショットを使う。世代の切り替えにはGo標準ライブラリのatomic pointerを使い、独自のイベント基盤は作らない。

### 更新間隔と失敗時の扱い

`recording serve`の起動直後に1回更新し、その完了から既定1時間後に次の更新を始める。同時に2回は実行しない。更新間隔は5分以上24時間以下で明示変更できる。

1回の更新期限は10分とする。通信切断、応答停止、不正データ、件数超過、DB書き込み失敗、チャンネル照合失敗では、その回だけ失敗する。短い間隔の自動再試行は行わず、次の予定時刻まで待つ。録画スケジューラとCtrlCmdは、直前の利用可能な番組表で動き続ける。

起動時に利用可能な完了世代がない場合は、従来どおり待受を開始しない。利用可能な完了世代があり、起動直後の更新だけが失敗した場合は、待受と録画を継続する。

### 停止と観測

プロセス停止時は、CtrlCmd受付、番組表更新、録画スケジューラの順序を一つの親contextで止め、受付済み処理だけを既存の終了期限内で待つ。終了時に新しい番組表を完了扱いへ押し進めない。

更新結果は、成功・失敗、サービス件数、番組件数、所要時間、安定した失敗理由だけを出力する。接続先、番組名、放送局名、生の応答、チャンネル設定、絶対パスは出力しない。

## 影響

### 良い影響

- 録画プロセスを止めずに番組表を更新できる。
- 更新失敗や設定不一致が、前回の番組表と進行中の録画を壊さない。
- 一つのCtrlCmd要求内でチャンネルと番組の世代が一致する。
- 新しいDB形式や外部依存を増やさずに実装できる。

### 負担

- 世代IDを明示する読み取りAPIと、動的スナップショットのテストが必要になる。
- `recording serve`は録画開始時だけでなく、起動直後と定期更新時にもMirakurunへ接続する。
- 古い完了世代の削除は、利用中スナップショットを考慮する別の保守作業になるため、この変更では行わない。

## 採用しなかった案

- **番組表更新を別プロセスにする:** SQLite所有権、停止順、設定、障害の切り分けが増えるため不採用。
- **各問い合わせで最新世代を読む:** 一つの要求内で世代が混ざるため不採用。
- **完了後にチャンネル照合する:** 不適合な完了世代が再起動後の利用を妨げるため不採用。
- **新しいactive世代テーブルを追加する:** 今回は`RUNNING`世代の事前検証と世代固定読み取りで同じ不変条件を満たせるため不採用。
- **更新失敗時にすぐ再試行する:** 障害中のMirakurunとSQLiteへ負荷を重ねるため不採用。

## 検証

- 更新成功時だけ新しい世代へ切り替わることを、更新前・更新中・完了直後の同時要求で確認する。
- 取得失敗、期限切れ、取消し、件数超過、チャンネル不一致、DB失敗で以前のスナップショットを維持する。
- CtrlCmdの一要求、予約追加、番組検索が同じ世代だけを読むことを競合検出テストで確認する。
- 録画中の更新、更新中の録画開始、再起動、停止を合成環境と実験環境で確認する。
- 通常、順序変更、競合検出、静的検査、脆弱性検査、CGO無効の4環境ビルドを同じ製品コミットで行う。
