# ADR-0045: 予約変更操作の成功本文を32ビット整数へ統一する

- Status: Accepted
- Date: 2026-08-10
- Decision owners: Project owner
- Accepted by: Codex（委任されたv1.0までの技術判断）
- Supersedes: なし
- Superseded by: なし

## 背景

Komorebi 1.1.0-beta6は、単発予約の追加2013、変更2015、削除1014が成功すると、応答本文から32ビット整数の`1`を読む。Sazanami v0.0.24は2013と2015へ16ビットのversion `5`、1014へ空本文を返すため、保存後にクライアントが失敗と解釈する。

KonomiTV v0.14.1は三つの操作で結果コードを確認し、成功本文を利用しない。クライアントを要求から識別して応答を分ける根拠はなく、共通の4バイト本文を返す方が単純である。

## 決定

2013、2015、1014が保存に成功した場合は、CtrlCmdの結果コード`1`に加え、本文へlittle-endianの32ビット整数`1`を一つ返す。

入力不正、保存失敗、対象なしの応答は変更しない。結果コード`0`と空本文を返す。応答書込みが失敗しても、確定済みの予約操作を自動再実行または巻戻ししない。

## 理由

一つの固定応答でKonomiTVとKomorebiの両方を満たせる。既存の予約・録画・DB処理を変えず、保存後の曖昧な失敗と重複再操作の危険だけを減らせる。

## 影響

- Komorebiは予約追加、変更、削除の成功をその場で読める。
- KonomiTVは従来どおり外側の成功結果を読める。
- 成功本文の互換形式を、三つの操作で同じ小さい関数と契約テストに固定できる。
- 未確認のEDCBコマンドや予約設定の対応範囲は広がらない。

## 採用しなかった案

### クライアントごとに本文を変える

要求からクライアントを確実に識別できず、同じ値で両方を満たせるため採用しない。

### 1014だけ従来の空本文を保つ

Komorebiの読み戻し補正に依存し、画面上の一時失敗と不要な2011を残すため採用しない。

### 応答失敗時に保存処理を再実行する

追加予約を重複させる可能性があるため採用しない。現在状態は2011で確認する。

## 検証条件

- 三つの成功フレームを固定byte列と構造読取りの両方で確認する。
- KonomiTVとKomorebiの期待値を別テスト名で固定する。
- 失敗、取消し、書込み切断で保存処理の呼出し回数が増えないことを確認する。
- 固定した両クライアントで追加、変更、削除を一巡する。
