# ADR-0044: 番組表の複数サービス指定を上限付きで受け付ける

- Status: Accepted
- Date: 2026-08-10
- Decision owner: Project owner

## 背景

Komorebi 1.1.0-beta6は、CtrlCmd 1029で複数チャンネルの番組表を一度に取得する。要求本文には、対象サービスごとの48ビットキーと、全サービスに共通する開始・終了時刻が入る。

Sazanami v0.0.23が受け付けるのは、KonomiTVの全件指定と1サービス指定だけである。公式Komorebi APKから複数サービスを要求すると、Sazanamiは本文の長さが違うため接続を閉じる。Komorebi側では応答ヘッダーを読めず、番組表を表示できない。

## 判断

1029で、1件以上4,096件以下のサービス指定と一つの時刻範囲を受け付ける。各指定は`0`と48ビットのサービスキーの組とし、重複や範囲外の値は番組表を読む前に拒否する。未知のサービスは結果から省く。

要求開始時に一つの完成済み番組表世代を固定する。指定されたサービスだけを既存の二回走査へ渡し、応答の大きさを先に確定してから逐次出力する。KonomiTVの全件指定、既存の1サービス指定、番組情報の変換形式は変えない。

## 理由

Komorebiが実際に送る形式だけを追加すれば、EDCBの未確認機能まで広げずに番組表を利用できる。既存の完成済み世代、件数上限、二回走査、逐次出力をそのまま使えるため、DB変更や番組全件のメモリ保持も不要である。

## 影響

- Komorebiは複数チャンネルの番組表を一度に取得できる。
- 要求本文の最大値は65,560バイトになるが、既存の1 MiB本文上限内に収まる。
- サービスキーの小さな集合を要求ごとに保持する。上限は4,096件で固定する。
- 番組数262,144件、応答本文256 MiB、同時生成1件の上限は変わらない。
- 画面操作からMirakurun／mirakcへ新しい通信を始めない。

## 採用しなかった案

### 1サービスずつ要求するようKomorebiを変更する

固定した公式クライアントをそのまま使う目標を満たさないため採用しない。

### 1029の任意の整数列を受け付ける

未確認の指定形式まで成功させ、入力上限と互換範囲が曖昧になるため採用しない。

### 番組をすべて集めてから要求順に並べる

応答上限に近い場合に不要なメモリを使う。クライアントは要求順を必要とせず、既存の決定的な応答順で足りるため採用しない。

## 検証

- 1件、複数件、4,096件と一件超過を確認する。
- 組の形式、重複、48ビット範囲、時刻範囲、長さ、途中切断を確認する。
- KonomiTV全件指定、既存1件指定、未知サービスを回帰確認する。
- 既存のページ読取り、二回走査、応答上限、取消し、切断、同時生成のテストを維持する。
- 公式Komorebi APKから番組表と予約画面を開き、バックエンド起因のエラーがないことを確認する。

## 製品への複製

このADRと対応するAccepted仕様を同じhandoffで製品へ複製する。調査記録、Android設定、接続先、番組情報、生の要求・応答は複製しない。
