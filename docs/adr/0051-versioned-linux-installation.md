# ADR-0051: Linux配布は版別directoryと明示DB更新を使う

- Status: Accepted
- Date: 2026-08-11
- Deciders: Project owner（v1.0までの判断をCodexへ委任）

## 背景

Sazanami DVRはLinux向け配布アーカイブと、DBの状態確認、更新、バックアップ、復元コマンドを持つ。OS再起動後の自動起動例と、実行ファイルとDBを一緒に安全に更新・切り戻す公開手順はまだない。

実行ファイルを上書きし、サービス起動時にDBまで自動更新すると、起動に失敗したときに以前の組合せへ戻しにくい。通常のアンインストールでデータを消すと、再導入や障害調査もできなくなる。

## 判断

Linuxの標準配置を次のように定める。

| 用途 | path | 更新時の扱い |
|---|---|---|
| 版ごとの配布物 | `/opt/sazanami-dvr/<version>/` | 新しいdirectoryへ展開し、旧版を残す |
| 選択中の実行ファイル | `/usr/local/bin/sazanami-dvr` | 版別実行ファイルへのリンクを切り替える |
| 設定 | `/etc/sazanami-dvr/` | 初回だけ例から作り、更新では上書きしない |
| DB、バックアップ、既定の録画先 | `/var/lib/sazanami-dvr/` | 更新、切り戻し、通常削除で残す |

常駐処理は`sazanami-dvr`専用利用者で起動する。systemd unitは`recording serve`だけを実行し、`Restart=on-failure`、5秒の再起動間隔、SIGTERM、2分の停止期限、`UMask=0077`を使う。DB migrationを`ExecStartPre`や起動scriptから実行しない。

環境設定例には、data root、録画先、チャンネル設定、Mirakurun URLと、ADR-0049で採用した3つの既定ポートを記載する。systemd unitはCtrlCmdの`0.0.0.0:4520`と録画HTTPの`127.0.0.1:4521`を明示して起動する。WebUIの`127.0.0.1:4522`は手動起動用として同じ設定例へ置くが、このunitからWebUIは起動しない。

ADR-0050のチューナー数自動取得を通常のsystemd起動でも使うため、基準unitと環境設定例には`--max-concurrent-recordings`を含めない。未指定時はflag自体を渡さず、空の環境変数で代用しない。同時録画数を固定する利用者だけが、systemd drop-inで`ExecStart`全体を明示的に置き換え、正の値を追加する。基準unitへshellや、複数の起動引数をまとめた環境変数は加えない。

更新は次の順で行う。

1. 録画中でないことを確認し、サービスを停止する。
2. 旧版で手動バックアップを作り、backup IDを記録する。
3. 新版を別directoryへ展開し、`--version`を確認する。
4. 新版で`db status`を実行し、必要な場合だけ`db migrate`を明示実行する。
5. 実行ファイルとunitのリンクを新版へ切り替え、サービスを起動する。
6. 起動状態と主要な待受を確認する。

DB形式を変えた更新から切り戻す場合は、新版の`db restore`で更新前バックアップを復元し、旧版の`db status`が`CURRENT`になってからリンクを旧版へ戻す。録画ファイルは切り戻さない。DB形式が変わっていなければ、停止後にリンクだけを旧版へ戻せる。

通常のアンインストールはサービスを停止・無効化し、unit、実行ファイルのリンク、`/opt/sazanami-dvr/`の配布物だけを削除する。`/etc/sazanami-dvr/`、`/var/lib/sazanami-dvr/`、別に指定した録画先、バックアップ、`sazanami-dvr`利用者は残す。

設定とデータを消す操作は「purge」と呼び、通常削除とは別の明示手順にする。purgeでは、利用者が削除対象の絶対pathを確認した場合だけ、設定、DB、バックアップ、録画、最後に専用利用者を削除する。glob、未確認の環境変数、広い親directoryを削除対象にしない。

## 理由

版別directoryとリンク切替なら、新版を旧版と並べてversion確認できる。DBの更新を停止中の明示操作へ分ければ、バックアップIDと結果を確認してから起動できる。systemdの標準機能だけで常駐化できるため、独自installerや更新daemonも不要である。

通常削除でデータと利用者を残せば、誤操作による録画消失を避け、再導入後も同じ所有権で読み戻せる。完全削除が必要な場合は、purgeを明示的に選べる。

## 影響

- 初回導入ではsystemdとroot権限を使うOS操作が必要になる。
- 更新時は短時間サービスを止め、DB状態を人が確認する。
- 旧版の配布物は自動削除しないため、正常確認後に利用者が整理する。
- systemd以外の環境では、同じ引数を別のサービス管理機構へ手動で設定する必要がある。
- 録画後の電源動作には、別途systemd／polkitの権限設定が必要になる場合がある。

## 採用しなかった案

### `.deb`とAPT repositoryを作る

初版の単一実行ファイルには配布、署名、repository運用が大きすぎる。配布アーカイブとhash照合で始める。

### 実行ファイルへ自己更新を組み込む

root権限、download、署名、途中失敗を製品機能へ持ち込むため採用しない。

### 通常削除で全データを消す

利用者がアンインストールだけを意図した場合にも録画を失うため採用しない。
