# ADR-0050: Mirakurunのチューナー一覧を同時録画の初期上限に使う

- Status: Accepted
- Date: 2026-08-11
- Decision owners: Project owner
- Delegated reviewer: Codex
- Related: ADR-0023、ADR-0031、Plan 0065、Handoff 0040
- Product copy path: `docs/adr/0050-startup-tuner-count-default.md`
- Product sync state: NOT COPIED

## 背景

ADR-0031は、同時録画数を利用者が明示する1～8の値とし、既定値を1に固定した。当時は
Mirakurunの利用中状態や他の利用者までSazanamiから正確に予測できないため、チューナー数の
自動検出を採用しなかった。

この制約は安全な初版には役立ったが、複数チューナー環境でも同じ値を毎回指定する必要がある。
Project ownerは、Mirakurunの設定済みチューナー数を起動時の初期値に使い、実際の割り当て判断は
引き続きMirakurunへ任せる方針を明示的に採用した。これは空きチューナーの予測ではなく、
利用者が省略した設定を補う処理である。

固定source調査では、Mirakurun 4.1.3とmirakc 3.4.78の`GET /api/tuners`はtop-level JSON arrayを
返す。一覧取得はチューナーを開かないが、streamを割り当てられることまでは保証しない。

## 判断

`recording serve`で`--max-concurrent-recordings`が明示された場合は、その正の値を最優先する。
自動判定用の`GET /api/tuners`は行わない。従来のflag名を維持し、固定上限8は撤廃する。

flagが未指定の場合だけ、起動時に`GET /api/tuners`を一度実行する。top-level arrayを逐次読み、
JSON object一要素をチューナー一台として数える。`types`の要素数や`isFree`、`isUsing`、`isFault`、
`isRemote`などの瞬間状態で値を増減しない。実行中の再取得と自動retryは行わない。

一件以上を正常に読み切った場合は、その件数をschedulerと録画stream adapterの同時上限へ渡す。
空配列、構造不正、上限超過、通信失敗、操作期限超過では、途中値を捨てて1を使う。
このfallbackで録画サービスの起動を止めない。ただし、プロセス終了による親contextの取消しは
fallbackへ変換せず、起動を中止する。

20以上の値は拒否も縮小もせず、そのまま使う。ただし、録画ごとの接続、buffer、file descriptor、
Go routineが増える可能性を、接続先や番組情報を含まない注意として起動時に一度だけ出す。

設定値に比例するchannel、slice、mapを起動時に確保しない。完了通知と停止通知は、小さい固定構造か
実際の録画開始数に応じて増える構造にする。実際のstream要求は従来どおり録画ごとに独立させ、
Mirakurunの割り当て結果を最終判断とする。先に始まった録画の中断、優先度による割込み、
同一serviceのstream共有は追加しない。

チューナー一覧は、既存Mirakurun adapterと同じURL検証、redirect拒否、proxy無効、TLS検証、
content type検証、header／body／deadline上限を使う。本文は1 MiB、応答headerは64 KiB、
接続と応答開始は5秒、操作全体は5秒とする。全配列をメモリへ載せず、応答内容を保存しない。

DB schema、録画file形式、CtrlCmd、Native REST API、KonomiTV／Komorebiの公開形式、
ライブ中継の既存上限は変更しない。

本ADRは、ADR-0031のうち「既定値1」「指定範囲1～8」「チューナー数の自動検出を不採用」とした
部分だけを変更する。DB確保後の起動、録画ごとの独立実行、枠不足、停止、復旧、先着録画を
中断しない判断はADR-0031のまま維持する。両文書の同時録画数に関する記述が異なる場合は、
本ADRを新しい差分判断として適用する。ADR-0031の完了証拠は書き換えない。

## 結果

- 複数チューナー環境では、flagを省略しても設定済み台数を初期上限にできる。
- 明示値は常に優先され、自動取得を避けたい運用では従来のflagをそのまま使える。
- Mirakurunが到達不能でも、既定一件で録画サービスを起動できる。
- 設定済み台数と実際の空き台数が違う場合、録画開始時にMirakurunが拒否する可能性は残る。
- 固定上限を外すため、利用者が大きい値を明示した場合の運用負荷は利用者が管理する。
- 起動時のnetwork要求が一回増えるのは、flag未指定の`recording serve`だけである。

## 採用しなかった案

### 既定値1と最大8を維持する

初版の挙動は保てるが、設定済みチューナー数を毎回転記する手間が残る。Project ownerの採用判断に
合わない。

### 放送種別と瞬間状態から利用可能数を計算する

一台が複数の放送種別を持つ場合に過大計上しやすい。他の利用者や同一周波数共有も一覧だけでは
判断できないため、配列要素数だけを初期値にする。

### 運転中に一覧を再取得して上限を変える

上限の増減と実行中録画の関係が複雑になる。起動時に一度だけ決め、変更は再起動または明示flagで行う。

### 20で切り詰める

正当な大規模構成を拒否する根拠がない。20以上は注意だけにする。

## 検証

- 明示値ではHTTP要求が0回で、1、8、9、20、20超を受け付ける。
- 未指定では一回だけ取得し、配列要素数を`types`や状態fieldと無関係に数える。
- 空、不正、通信失敗、操作期限超過では1へ戻り、途中件数を使わない。
- 親contextの取消しでは起動を中止する。
- 20以上の自動値と明示値で、注意を一度だけ出す。
- 大きい正の設定値でも、起動時メモリをその値に比例して確保しない。
- fake HTTPでstatus、content type、本文、期限、切断、close、Go routine残留を確認する。
- 実環境の一覧件数は、stream割り当て能力の成功として報告しない。

## 見直す条件

- Mirakurun／mirakcの一覧形式がtop-level arrayでなくなる。
- 実際の同時割り当て能力を安定して返す別capabilityが契約化される。
- 大規模環境の測定で、注意だけでは通常運用を守れない証拠が得られる。
- 複数backend、同一周波数共有、予約優先度を扱うplannerを導入する。
