# ADR-0061: 新しく追加した放送中予約は現在時刻から録画する

## 背景

Sazanami v0.2.0は、録画予定開始から5分を超えた予約を`MISSED / LATE_START_EXPIRED`とする。この境界は
再起動後に古い予約を突然始めないために必要である。一方、KonomiTVで放送中の番組へ録画操作を行うと、
番組本来の開始時刻を持つ新規予約が作られる。番組が始まって5分を超えていれば、利用者が今から録画する
意図を持っていてもstreamを一度も開かず未実行になる。

実験環境では、KonomiTVから追加した三件がすべてこの理由で0 byteのまま終わった。予約作成とCtrlCmd通信は
成功しており、問題はschedulerの遅延判定にあった。

## 判断

新しく追加した放送中予約は、現在時刻から録画を始める。次の条件をすべて満たす場合、予定開始から
5分を超えていても既存のclaimと録画処理へ進める。

- 予約作成時刻が、余白反映後の予定開始以降である。
- 予約作成時刻が現在より後ではない。
- 予約作成から現在までが5分以内である。
- 余白反映後の予定終了まで60秒以上ある。
- その予約に録画処理がまだ存在しない。

録画履歴の予定開始と予定終了は元の番組時刻と余白から作り、実開始時刻だけを実際の開始時刻とする。
番組冒頭を補完せず、現在取得できるTSから保存する。

上記以外の遅延予約には従来の5分上限を維持する。とくに、番組開始前に作成されてdaemon停止中に古くなった
予約、作成から5分を超えてschedulerへ届いた予約、未来または不正な作成時刻は救済しない。予定終了まで
60秒未満なら、作成直後でも開始しない。

録画中の削除は既存のCtrlCmd 1014を使う。開始前は予約取消し、録画中は一件だけを停止し、188 byte以上の
安全な部分録画を`PARTIAL / USER_REQUESTED_STOP`として残す。本判断はこの意味を変えない。

## 理由

予約作成時刻はSQLiteへ永続化済みであり、新しいflagやschemaなしで利用者の直近操作と古い予約を区別できる。
既存の5分を作成後の処理猶予にも再利用すれば、新しい設定を増やさず、DBやschedulerの一時的な停止を
無制限に救済しない。

## 結果

- KonomiTV、Native API、自動予約のいずれから追加しても、同じ保存済み時刻条件を使う。
- 放送中の途中から録画できる。
- 再起動後の古い予約を一斉に開始しない。
- DB、CtrlCmd、Native API、provider、ファイル形式は変わらない。
- 予定開始と実開始の差が大きい履歴を正しく保持する。

## 採用しなかった案

### 遅延上限を全面的に削除する

古い予約と利用者の直近操作を区別できず、再起動時の挙動が危険になるため採用しない。

### Clientが開始時刻を現在へ変更する

番組の本来の時刻を失い、clientごとに異なる挙動になるため採用しない。

### 途中録画専用flagを追加する

保存済みの作成時刻で十分に判定でき、schemaと互換境界を増やすため採用しない。

## 検証

- 新規の放送中予約、作成後5分境界、古い未来予約、未来の作成時刻を確認する。
- 残り60秒境界を確認する。
- 予定開始と実開始が別々に保存されることを確認する。
- 1014による開始前取消し、録画中停止、部分録画公開を回帰確認する。
- 実験環境では番組情報や接続先を記録せず、状態、固定理由、byte数、時刻差だけを確認する。

## 見直す条件

- 作成時刻以外に、途中録画の明示操作を表す公開契約が採用される。
- 残り60秒未満も録画する利用者要件が明示される。
- 再起動後の途中録画再開が別のAccepted判断で採用される。
