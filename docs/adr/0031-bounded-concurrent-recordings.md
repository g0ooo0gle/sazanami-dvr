# ADR-0031: 複数同時録画は明示上限内の独立実行にする

- Status: Accepted
- Date: 2026-08-09
- Decision owners: Project owner
- Delegated reviewer: Codex
- Related: ADR-0028、ADR-0030、Plan 0044、Handoff 0019

## 背景

v0.0.6は一件の予約を安全に確保し、Mirakurun streamを部分ファイルへ保存できる。予約、録画処理、録画区間、ファイル名は録画ごとに独立しているが、スケジューラとstream adapterが同時実行を一件へ制限している。

複数チューナーを持つ環境では、重なった番組の一方を常に`RECORDING_SLOT_UNAVAILABLE`にする制限を外したい。ただし、チューナー数を推測した自動拡張、無制限のGo routine、予約優先度による割込みは、負荷と失敗時の復旧を複雑にする。

## 判断

同時録画数は利用者が明示できる1～8の固定上限とし、既定値は1を維持する。

スケジューラは録画処理をDBへ同期的に確保してから、一件の独立したGo routineで実行する。実行中の件数だけをメモリで数え、予約の正本と録画状態はSQLiteに置く。内部の待ち行列と常駐worker poolは作らない。上限を使い切った時点で開始時刻に達した予約は、従来の安定した理由`RECORDING_SLOT_UNAVAILABLE`で未実行として確定する。

Mirakurun stream adapterは同じ上限までHTTP接続を許可する。各録画のlease、context、部分ファイル、進捗、再接続回数は共有しない。一件の再接続は、古いleaseを閉じてから次を開く既存契約を維持する。

通常の録画失敗はその録画だけの終了状態にする。DBの確保や状態更新など、正本を維持できない失敗では新しい録画を開始せず、実行中の録画をcancelしてプロセスを停止する。停止時は全実行の終了を待ってからDBと録画保存先を閉じる。

DB schema、録画ファイル形式、CtrlCmdの公開形式、外部依存は変更しない。

## 結果

- 既定値1ではv0.0.6と同じ負荷と挙動を維持できる。
- 上限内では録画ごとに成功、失敗、再接続、完成処理を分離できる。
- 同時数を増やした結果Mirakurunが拒否した場合、その録画だけが既存のストリーム失敗理由で終了する。
- SQLite writerは短い更新を直列化するため、同時録画数を増やしてもDB transactionは並行書込みしない。
- 最大8本分のHTTP接続、録画用buffer、file descriptor、Go routineを使う可能性がある。利用者は提供元と保存先の能力を確認して明示指定する必要がある。

## 採用しなかった案

### チューナー数を自動検出する

不採用。Mirakurunの利用中チューナー、優先度、ほかの利用者をSazanamiだけで正確に判断できない。既定1と明示上限の方が予測しやすい。

### 予約をメモリqueueへ積み、固定worker poolで処理する

不採用。予約と所有権の正本がDBとqueueへ分かれる。開始時刻に達した予約だけをDBから読み、確保後に小さい実行単位を起動すれば足りる。

### 同じserviceのstreamを複数録画で共有する

不採用。終了時刻、再接続、cancel、書込み失敗の所有関係が複雑になる。初版は録画ごとに独立したMirakurun接続を使う。

### 優先度の低い録画を中断して枠を空ける

不採用。完成ファイルとKonomiTV表示の扱いを別途設計する必要がある。初版は開始時点の空き枠だけで決める。
