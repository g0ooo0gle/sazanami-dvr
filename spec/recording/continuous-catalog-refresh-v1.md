# 録画中も番組表を更新するための仕様 第1版

- Status: Accepted
- Accepted date: 2026-08-09
- Decision owner: Project owner
- Delegated reviewer: Codex
- Product destination: `spec/recording/continuous-catalog-refresh-v1.md`
- Related decision: [`../../docs/adr/0027-continuous-catalog-refresh.md`](../../docs/adr/0027-continuous-catalog-refresh.md)

## 目的

一つの`recording serve`がSQLite、録画、CtrlCmd、Mirakurun番組表更新を所有し、録画を止めずに番組表を更新できるようにする。失敗した更新や途中の更新は公開せず、利用可能だった直前の番組表を維持する。

## 利用者から見える動作

- 起動済みの録画プロセスが、起動直後と一定間隔で番組表を更新する。
- 更新中も番組表、予約、録画中表示を利用できる。
- 更新に失敗しても、前回正常に完了した番組表で予約と録画を続ける。
- 更新に成功した後の新しい要求から、新しい番組表が見える。
- 手動の`catalog sync`コマンドは残すが、録画プロセスと同じDBへ同時に接続する操作には使わない。

## 要件

| ID | 要件 |
|---|---|
| `CCR-001` | `recording serve`はSQLiteを一度だけ開き、同じプロセスで番組表更新、予約、録画、CtrlCmdを実行する。 |
| `CCR-002` | 更新中の世代は、チャンネル設定との照合に成功するまで`COMPLETED`にしない。 |
| `CCR-003` | 一つのCtrlCmd要求または予約追加は、一つの番組表世代だけを読む。 |
| `CCR-004` | 更新の失敗、取消し、期限切れでは、直前の利用可能なスナップショットを維持する。 |
| `CCR-005` | 起動直後と設定間隔で一回ずつ更新し、同時更新と失敗直後の追加再試行を行わない。 |
| `CCR-006` | 出力は件数、所要時間、安定した理由に限り、接続先、番組情報、生の応答、絶対パスを含めない。 |

## 固定する上限

| 項目 | 値 |
|---|---:|
| サービス取得ページ | 256件以下 |
| サービス総数 | 4,096件以下 |
| 番組取得ページ | 256件以下 |
| 番組総数 | 262,144件以下 |
| 1回の更新期限 | 10分 |
| 既定の更新間隔 | 1時間 |
| 設定できる最短間隔 | 5分 |
| 設定できる最長間隔 | 24時間 |
| 同時更新数 | 1 |
| 更新失敗直後の追加再試行 | 0回 |

既存のHTTP本文上限、deadline、redirect拒否、proxy環境変数を暗黙利用しない設定、TLS検証を維持する。

## 起動順

1. SQLiteを一度だけ開き、残っている`RUNNING`世代を`FAILED`へ閉じる。
2. 最新の利用可能な完了世代とチャンネル設定を照合し、初期スナップショットを作る。
3. 録画の復旧を行う。
4. CtrlCmdと録画スケジューラを開始する。
5. 同じ親contextの下で番組表更新処理を開始し、最初の更新を直ちに行う。

1〜3が失敗した場合は待受を開始しない。5の更新が失敗しても、2で作ったスナップショットを使って待受と録画を続ける。

## 1回の更新

1. 更新専用の10分contextを作る。
2. 既存のMirakurun catalog adapterでサービスを取得し、`RUNNING`世代へ保存する。
3. 番組を取得し、同じ世代へ保存する。
4. その世代のサービスを最大4,096件まで読み、チャンネル設定と照合する。
5. 世代IDを保持する候補スナップショットを作る。
6. 世代の保存件数を照合し、`COMPLETED`へ変更する。
7. 候補スナップショットを一度のatomic storeで公開する。

4または5が失敗した場合は6と7を行わない。6が失敗した場合は7を行わない。7はメモリ内の一回の代入だけとし、失敗する処理を含めない。

更新終了後に1時間のtimerを開始する。更新時間が延びても同時更新は起動しない。間隔を変更した場合も、次の開始は直前の更新終了から測る。

## 世代を固定した読み取り

スナップショットは次を保持する。

- backend ID
- catalog sync generation ID
- 検証済みチャンネル一覧
- チャンネル設定と一覧から求めた不透明なsnapshot key

SQLiteのサービス・番組読み取りは、指定した世代IDが同じbackendの`COMPLETED`世代であることをSQL内で確認する。更新前の候補を作るためのサービス読み取りだけは、指定した同じbackendの`RUNNING`世代を許可する。

CtrlCmd routerは要求を解析した直後に現在のスナップショットを一度だけloadする。チャンネル一覧、番組一覧、番組検索は、応答が終わるまでそのスナップショットを使う。予約追加も、入力検証後に一度だけloadして番組を照合する。

切り替え前に開始した操作は古い世代、切り替え後に開始した操作は新しい世代を使う。途中で混在させない。

## 失敗理由

外部へ出す理由は次の安定した値にまとめる。

| 理由 | 意味 |
|---|---|
| `catalog-refresh-provider-failed` | 接続、HTTP、JSON、取得期限、取得上限の失敗 |
| `catalog-refresh-store-failed` | 世代開始、保存、件数照合、完了の失敗 |
| `catalog-refresh-channel-mismatch` | 新しいサービスとチャンネル設定を照合できない |
| `catalog-refresh-canceled` | 親contextによる停止 |
| `catalog-refresh-internal` | 上記へ安全に分類できない内部失敗 |

providerの生エラー、URL、HTTP本文、番組情報、DB pathは通常出力へ含めない。終了時の取消しは異常終了として繰り返し出力しない。

## 停止と再起動

- 親contextを取り消すと、新しい更新を開始しない。
- 進行中のHTTP、cursor、DB操作は同じcontextで中止する。
- 中止した`RUNNING`世代は可能な範囲で`FAILED`へ閉じる。プロセス終了が先の場合は次回起動時に閉じる。
- 完了前の候補スナップショットは公開しない。
- 再起動時は最新の利用可能な`COMPLETED`世代から初期スナップショットを再構築する。

## 必須テスト

### 単体とSQLite統合

- 初回更新、2回目更新、空の正常世代、順序が異なる同一内容。
- 取得失敗、途中切断、stall、取消し、期限切れ、サービス・番組の上限ちょうどと1件超過。
- チャンネル不足、重複、TSID不足、不正な世代ID、別backendの世代ID。
- 保存失敗、完了失敗、切り替え直前の取消し、停止後に新しい更新を始めないこと。
- 失敗した更新後も、以前のチャンネル、番組、予約追加を利用できること。
- 再起動時に残った`RUNNING`を閉じ、最新の正常世代を選ぶこと。

### 並行処理

- 更新中のCtrlCmd要求が古い一世代だけを読む。
- 切り替え後の要求が新しい一世代だけを読む。
- 長い番組一覧応答中に切り替えても世代が混ざらない。
- 更新中に予約追加と録画開始が重なっても、重複試行やpanicを起こさない。
- 100回以上の更新でgoroutineとファイル記述子が増え続けない。

### コマンドと実環境

- `recording serve`だけが、起動直後と設定間隔で番組表へ接続する。
- `--catalog-refresh-interval`の5分、24時間、範囲外、不正値を確認する。
- 既存の`catalog sync`、`ctrlcmd serve`、`ui serve`が暗黙の定期更新を始めない。
- 実験環境で録画中に番組表を更新し、録画完了、KonomiTVの番組表、予約一覧、録画済み再生を確認する。

## 対象外

- 通信切断後の録画ストリーム再接続。
- 番組時間の変更を既存予約へ反映する処理。
- 複数同時録画、自動予約、録画履歴API。
- チャンネル設定の実行中再読み込み。
- 古い番組表世代の削除方針。
- WebUI、CtrlCmd、録画を新しい共通frameworkへ載せ替えること。
